# EP-04: Authentication

## 1. Summary

This epic lets real people sign in. The prototype has no login: a chip at the foot of the rail lets anyone become the
owner, a staff member or a karigar with one click. The user asked for "a proper user authentication mechanism"
instead of role switching. Because only the owner may clear a mismatch, apply a tag edit or scrap a piece, the shop
needs to know for certain who is acting. This epic covers sign-in (by phone and WhatsApp OTP if D4 is confirmed),
OTP send and verify, sessions, sign-out, lockout after failed attempts and the one-time creation of the first owner.

## 2. Layer, milestone, status

- Layer: A · Platform foundation
- Milestone: M1 Platform
- Prototype status: Not built. Identity is chosen from the `RoleChip` menu through `StoreProvider.switchIdentity`; there is no login, no OTP for sign-in and no session.

## 3. Roles involved

- Owner: signs in (OTP, plus a password fallback if D4 adopts it); the first owner is bootstrapped once.
- Staff: signs in by phone and OTP on the shop device or their own.
- Karigar: signs in to the job portal on their phone by phone and OTP.
- System: generates and checks OTPs, issues and expires sessions, locks out after failed attempts, ends sessions when a user is deactivated or changes role.

## 4. In scope

- Sign-in by the method D4 decides; the recommendation is phone plus WhatsApp OTP, with a password fallback for the owner.
- OTP generation: 6 digits, single use, 10-minute expiry, rate limited.
- OTP verification with results ok, wrong, expired.
- Sessions: issue on verify, expire after a set time, end on sign-out.
- Lockout after a set number of failed attempts.
- First-owner bootstrap: one owner account created once when the system is empty.
- Landing route per role after sign-in: staff `today`, owner `decisions`, karigar `k-jobs`.
- Ending all of a user's sessions at once when they are deactivated or their role changes.
- Signed-out, sign-in, OTP entry and locked-out states.

## 5. Out of scope

- Adding, editing, deactivating users and assigning roles (EP-05).
- The account menu that replaces the role switcher (EP-05).
- Permission checks per operation (EP-05).
- Real WhatsApp delivery of the OTP (EP-12); this epic uses a delivery stub until EP-12 exists.
- The notification service that routes the OTP message (EP-11).
- The edit token sent to the owner for tag edits (EP-25), which shares the OTP rules but not the flow.
- Rate-limit values across the whole API and penetration testing (EP-39).
- Offline sign-in for karigars (EP-20 under D6).

## 6. Current state in the prototype

- `src/components/ui/RoleChip.tsx`: "Avatar chip showing who is signed in; its menu switches between the staff, owner and karigar identities." It calls `switchIdentity` from `useStore()`.
- `src/store/StoreProvider.tsx`: `switchIdentity(id)` picks an identity from `identities()` and changes `identity`; the route jumps to the role's landing route. There is no credential check.
- `src/store/selectors.ts`: `identities()` builds the list of `Identity` records from staff and karigars; `actorOf()` turns the picked identity into the `Actor` passed to every transition.
- `src/types/jewellery.ts`: `Actor {id, name, role}`; `Identity extends Actor {initials, subtitle, karigarId?}`.
- `src/nav.ts`: `landingRoute = { staff: 'today', owner: 'decisions', karigar: 'k-jobs' }`.
- `src/components/ui/OtpPanel.tsx`: six boxes for code entry, paste support, and a simulated WhatsApp bubble showing the code; `validFor` defaults to "10 minutes". Used today by `edit-apply`.
- `src/domain/edits.ts`: `makeToken` (6 digits), `TOKEN_TTL_MS = 10 * MIN`, `checkToken` returning `ok`, `wrong`, `expired` or `none`. The token is stored in plain text on `PieceEdit.token`.
- Mockup `25-onboard-staff.svg`: "Phone · they sign in and get OTPs here". Mockup `24-onboard-karigar.svg`: "Phone · their job portal logs in with this". `10-navigation-map.mmd`: node `SIGN["Sign in"]` leads to the three homes.
- Reusable: `OtpPanel` for the OTP entry screen; the `checkToken` result set and the 10-minute expiry as the OTP model; `landingRoute` for post-sign-in routing.
- Must be rebuilt server-side: OTP generation with a secure random source, hashed storage, single use, attempt counting, lockout, session issue and expiry, bootstrap. `makeToken` derives digits from a counter and must not be used for real codes.

## 7. Functional requirements

- FR-04-1. A user can request a sign-in OTP by entering a phone number registered to an active user.
- FR-04-2. A request for an unknown or deactivated phone gives the same response as a known one, so the screen does not reveal which numbers exist.
- FR-04-3. The OTP is 6 digits, generated by the server from a secure random source.
- FR-04-4. The OTP is valid for 10 minutes and for one successful use only.
- FR-04-5. The server stores only a hash or reference of the OTP; the plain code never appears in the database, logs or audit.
- FR-04-6. Entering the correct, unexpired OTP creates a session and lands the user on `today` (staff), `decisions` (owner) or `k-jobs` (karigar).
- FR-04-7. Entering a wrong OTP shows "wrong code"; an expired one shows "code expired" and offers a new code.
- FR-04-8. After a set number of failed attempts on one phone, sign-in is locked for a set period and the screen says so.
- FR-04-9. OTP requests per phone and per device are rate limited.
- FR-04-10. A session expires after a set time and the next request returns unauthenticated.
- FR-04-11. A user can sign out, which ends that session at once.
- FR-04-12. When "User deactivated or role changed" is received for a user, every session of that user ends and open screens return to sign-in.
- FR-04-13. When no owner exists, the system allows exactly one first-owner bootstrap, and refuses it afterwards.
- FR-04-14. If D4 adopts it, the owner can sign in with a password as a fallback when OTP delivery fails.
- FR-04-15. Until EP-12 is live, OTP delivery uses a stub visible only in development and staging.

## 8. Business rules

- BR-04-1. OTPs are 6 digits, single use, expire after 10 minutes, are rate limited and are never logged in plain text. [PRODUCTION-SCOPE §5 Security]
- BR-04-2. Sessions expire; deactivating a user ends their sessions at once. [PRODUCTION-SCOPE §5 Security]
- BR-04-3. Recommended sign-in is phone plus WhatsApp OTP with a password fallback for the owner; not yet decided. [PRODUCTION-SCOPE §4 D4]
- BR-04-4. Staff sign in and receive OTPs on the phone recorded at onboarding. [mockup 25]
- BR-04-5. The karigar job portal logs in with the karigar's phone. [mockup 24]
- BR-04-6. Sign-in leads to one of three homes. [mockup 10-navigation-map.mmd; src/nav.ts landingRoute]
- BR-04-7. Scope includes lockout after failed attempts and first-owner bootstrap. [PRODUCTION-SCOPE §6 EP-04 scope]
- BR-04-8. Access must end at once when a user is deactivated or changes role. [PRODUCTION-SCOPE §1 live events]
- BR-04-9. There are three roles only. [SCOPE-ANALYSIS App. A]

## 9. Data

- OtpChallenge: id, userId, phone, code hash, issued at, expires at (issued plus 10 minutes), used at, attempt count.
- Session: id, userId, role at issue, created at, expires at, ended at, end reason (sign-out, expiry, deactivated, role changed), device label.
- Lockout: phone or userId, failed count, locked until.
- User (created in EP-02, read here): phone, role, status, optional password hash for the owner fallback.
- Bootstrap marker: whether the first owner has been created.
- No weights and no money fields in this epic.

## 10. API surface

Neutral to D1: each operation can be an endpoint on an own API or a function/policy on a managed platform.

| Verb | Resource | Purpose | Who may call |
| --- | --- | --- | --- |
| Create | OTP challenge | Send a sign-in OTP to a phone | Anyone (rate limited) |
| Verify | OTP challenge | Check the code and create a session | Anyone holding a challenge |
| Create | Password session | Owner password fallback sign-in, if D4 adopts it | Owner |
| Read | Current session | Who am I, my role, my landing route | Signed-in user |
| Delete | Current session | Sign out | Signed-in user |
| Delete | All sessions of a user | End access at once | System (on deactivation or role change) |
| Create | First owner | One-time bootstrap when no owner exists | Setup operator, once |

## 11. Live events

- Consumes: "User deactivated or role changed" — ends every open session of that user at once and sends their open screens back to sign-in.
- Emits: none. Sign-in and sign-out are recorded in the audit log (EP-06) but are not catalogue events.

## 13. Non-functional requirements

- Security: OTP 6 digits, single use, 10-minute expiry, rate limited, hashed at rest, never logged; session tokens are random and unguessable; sign-in responses do not reveal whether a phone is registered.
- Security: deactivation or role change ends sessions within about 1 second, the live event target. [PRODUCTION-SCOPE §5 Performance]
- Audit: sign-in success, failure, lockout, sign-out and bootstrap are written to the audit log with actor and time, never with the code.
- Personal data: staff and karigar phone numbers are personal data; they are not shown on the sign-in screen after entry.
- Performance: sign-in screen loads under 2 seconds on a shop connection.
- Time: OTP expiry and session expiry are computed on the server clock in UTC.

## 15. Epic acceptance criteria

1. Given an active staff member with phone P, when they request an OTP and enter it within 10 minutes, then they are signed in and land on `today`.
2. Given an OTP that was already used, when it is entered again, then sign-in is refused.
3. Given an OTP issued 11 minutes ago, when it is entered, then the screen says the code expired.
4. Given repeated wrong codes on one phone, when the lockout threshold is reached, then further attempts are refused until the lock period ends.
5. Given a signed-in karigar, when the owner deactivates them, then their phone returns to sign-in within about a second.
6. Given an empty system, when the first owner is bootstrapped, then a second bootstrap is refused.

## 16. Risks

- Risk: WhatsApp template approval for the OTP message takes weeks (D8), blocking sign-in. Mitigation: request the template early and keep the owner password fallback (if D4 adopts it) for launch.
- Risk: karigars share one phone in a workshop, so one phone maps to several users. Mitigation: raise it as an open question before EP-05 fixes phone uniqueness.
- Risk: the prototype token generator `makeToken` is reused for real OTPs and is predictable. Mitigation: a secure random generator in the server only.
- Risk: OTP codes leak into logs through request logging. Mitigation: redact the code field in all logs and test it in EP-40.
- Risk: lockout lets anyone lock out the owner by guessing on their phone. Mitigation: lock per phone and device, and keep the password fallback route separate.

## 17. Open decisions and questions

- D4: phone plus WhatsApp OTP, phone plus password, or email plus password? Is a password fallback kept for the owner?
- D8: which WhatsApp provider sends the OTP, and how long does template approval take?
- D1: is sign-in built on the managed platform's auth or in an own API?
- How many failed attempts trigger lockout, and for how long?
- How long does a session last, and is it different for the shop device, the owner and karigar phones?
- Can two karigars share one phone, and how does sign-in tell them apart?
- What happens when the owner loses their phone: who can recover the account?
- Who runs the first-owner bootstrap, and with which phone?
