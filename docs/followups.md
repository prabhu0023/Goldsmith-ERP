| FU-001 | Audit triggers can be switched off by the table owner. The app, migrations and tests all connect as `postgres` (superuser and owner of `audit_entries`), which can run `alter table audit_entries disable trigger …` and then update or delete audit rows. When real credentials arrive, the app must connect as a non-owner role with UPDATE, DELETE and TRUNCATE revoked on `audit_entries`; only migrations run as the owner. (EP-02 review finding 2.) | Deployment credentials: EP-04 (first real app credentials), EP-39 (security and data protection), deploy job EP-01-S12 | [#2](https://github.com/prabhu0023/Goldsmith-ERP/pull/2) |

| FU-003 | The rate-limit hook does not see every request. `GET /api/contract-version` resolves the session and answers without calling `rateLimiter`, and `POST /api/ops/:operation` with an unknown operation name answers 404 `not_found` before the hook runs, so neither is ever counted. EP-39 must run the hook for both (e.g. operation `readContractVersion`, and an unknown-operation bucket). (EP-03 review finding 4.) | EP-39 (security and rate limiting) | [#3](https://github.com/prabhu0023/Goldsmith-ERP/pull/3) |
| FU-004 | Production has no account email sender. With `ACCOUNT_EMAIL_MODE` unset in production the mailer is `disabled`: `createFirstOwner` and `requestPasswordReset` still answer `{ ok: true }` (mail goes out after the commit and is not awaited), the failure is only logged as `[api] account email failed`, and no activation or reset email reaches anyone. A first owner created in production cannot activate, and a resend needs an owner session (EP-05). The real sender must land before production setup, and should queue the mail (EP-10 jobs) so a failed send is retried. (EP-04 review findings 3 and 4.) | EP-11-S12 (real email sender) | EP-04 (branch `ep04-auth`) |
| FU-005 | The staging dev mailbox exposes every link. `/dev/mailbox` and `/dev/mailbox.json` are served without authentication whenever the stub mailer runs outside production (S4 allows staging), and `requestPasswordReset` is public, so anyone who can reach the staging api can reset and take over any account, owner included. Do not load real customer or staff data into staging while the stub is active; put the mailbox behind basic auth or limit it to development before then. (EP-04 review finding 5.) | EP-39 (security), staging deploy EP-01-S12 | EP-04 (branch `ep04-auth`) |
| FU-006 | The per-device sign-in and reset limits are per proxy address. The device key is `req.ip` and Express has no `trust proxy` setting, so behind the Vite dev proxy or a production reverse proxy every client shares one bucket: `AUTH_SIGN_IN_PER_DEVICE` (30) and `AUTH_RESET_PER_DEVICE` (10) per 15 minutes become limits for the whole installation, and one abuser can block sign-in for the shop. Set `trust proxy` for the real proxy when it is chosen. (EP-04 review finding 6.) | EP-39 (rate limiting), deployment EP-01-S12 | EP-04 (branch `ep04-auth`) |
| FU-007 | A signed-in user still acts on a prototype record. The account menu and the in-memory actor name now come from `session.user.name` (EP-05, branch `ep05-users`), so the shown and acting name are right. What remains: `identityFor` in `packages/web/src/store/StoreProvider.tsx` maps the real user to a prototype record id (and `karigarId`) by name and role, falling back to the first record of that role, so prototype screens such as the karigar phone read another person's records until screens read real data. (EP-04 review finding 7.) | EP-08 (front-end production foundation) | EP-04 (branch `ep04-auth`) |
